# Methodology note, Wave 1: A03 BOOT (phases 1 and 2)

Author: A03. Date: 2026-10-31. Branch `agent/a03/p1-boot`. Status: written before any code;
awaiting A01 (`Methodology accepted` or `rejected`).

## 1. Goal in observable terms

- `tools/ci/build-test.sh qemu64 debug` and `... max release` build the real kernel (not the
  placeholder), boot it from GRUB on QEMU and end with QEMU exit 33. The serial log holds the
  banner, one `KTEST` line per test and `KTEST-END`, and `ktest-run.py` judges it with the
  manifests in `tests/hal/` with zero problems.
- Deliberate failures end with exit 37 and a recognisable line: a failed `ASSERT`, a kernel page
  fault without fixup, a page fault at `DEVICE_LEVEL`, a double fault on its IST stack, a wrong
  `KeRaiseIrql` or `KeLowerIrql`.
- `#DE`, `#UD`, `#GP`, `#PF` are raised on purpose and each prints one decoded line (format in
  `docs/architecture/interrupts.md`), then the test resumes through a registered fixup.
- `HalQueryMonotonicTime` tracks the host clock within 1 % over 10 s (O4).
- A GDB session reaches `KiStartKernel` (recorded in `docs/architecture/boot-contract.md`).

## 2. Approach

**Entry names (proposal for A01 to record).** `KiBootEntry32` is the `ENTRY()` of `kernel.ld`
(32-bit code at its physical address, in `.boot`). `KiStartKernel(uint32_t MultibootMagic,
uint32_t MbiPhysical)` is the first C function, in `arch/x86_64/boot/start.c`.
The plan's provisional `KiStartKernel` is kept for the C side.

**Image and boot (ADR-0001, ADR-0002, Multiboot2 spec, Intel SDM vol. 3 ch. 9 and 4).**
`.boot` is linked at 1 MiB (VMA = LMA); the rest at `0xFFFFFFFF80000000 + phys` with `AT()`.
Four program headers (boot RX, text RX, rodata R, data RW) so GRUB loads at the physical address.
The trampoline checks EAX, checks CPUID long mode, builds PML4, PDPT, PD and PT in a `.pgtbl`
NOBITS section (not in BSS, so BSS clearing does not touch live tables), sets CR4.PAE, EFER.LME and
NXE, CR0.PG, WP, NE, loads a 64-bit GDT, far-jumps and enters the high half. Mappings: identity
0 to 4 GiB with 2 MiB NX pages (the loader's structures and legacy areas), the first 2 MiB in 4 KiB
pages with the first 64 KiB absent (null guard, ADR-0005), and the kernel image in the top 2 GiB with
4 KiB pages per section (text RX, rodata R NX, data RW NX), so W^X holds from the first C
instruction. Once the C code runs, the identity alias of the image is removed (it would be a writable
alias of `.text`). Direct map, pool and stacks stay A04's.

**Console and bug check.** COM1 16550 at 115200 8N1, polled transmit with a bounded wait so a
missing UART cannot hang. `ntoskrnl/rtl` holds the minimum: `memcpy`, `memset`, `memmove`, `memcmp`,
`strlen`, and a bounded `vsnprintf`-style formatter (pure, host-testable). `kprintf` formats into a
stack buffer and issues one console write with interrupts off, so lines never interleave.
`KeBugCheckEx` disables interrupts, prints one `KAMOS STOP` line and the parameters, paints the VGA
text screen, writes `HAL_EXIT_BUGCHECK` to `0xF4` and halts. Recursive bug checks halt at once.

**Boot information.** `HalpParseMultiboot2` in `hal/bootinfo.c` is a pure function (no kernel calls,
only `types.h`): it bounds every tag by the total size, checks alignment, the end tag, entry sizes,
wrap-around of `base + length`, counts against `BOOT_MAX_*`, then copies, sorts, merges and checks.
It returns a status and a reason code, so a host test can feed it hostile blobs (threat model B1,
O10). `HalInitializeBootInformation` wraps it and bug checks with
`KAMOS_STOP_BAD_BOOT_INFORMATION`. Merge rule (A01's decision, which refines `boot.h`): same-type
touching or overlapping regions are merged, any overlap of different types is a bug check, no
usable region is a bug check. The ACPI RSDP in the loader's tag is a copy; the address stored is
that of the firmware original, found by a checksum-validated scan of the EBDA and `0xE0000` area
that matches the copy, else 0.

**Exceptions (Intel SDM vol. 3 ch. 6).** GDT: null, kernel code `0x08`, kernel data `0x10`, user
data32 `0x18`... laid out so that `STAR[63:48] = 0x18` gives SYSRET the selectors `0x2B`/`0x23`
that A07 needs; TSS at `0x30`. TSS has RSP0 and IST1 (#DF), IST2 (NMI), IST3 (#MC). 256 IDT
gates, interrupt gates (IF cleared by the CPU), written from a NASM macro. Every stub normalises the
frame (dummy error code where the CPU pushes none: only vectors 8, 10 to 14, 17, 21, 29, 30 push
one), pushes the vector and all GPRs in one documented order (`KTRAP_FRAME`). Handlers run at
`DEVICE_LEVEL` (software level set on entry, restored on exit). ADR-0013 for `#PF`:
(1) exact-address fixup, `PASSIVE_LEVEL` only; (2) otherwise `KeBugCheckEx(UNHANDLED_EXCEPTION)`
with the decoded fault. The fixup table is a linker section `.kfixup` of `{fault_rip, resume_rip}`
pairs (for A04's copy routines, via a macro in `hal/halp.h`) plus 8 runtime slots used only by
tests, in two classes: `FIXUP` (follows ADR-0013) and `EXPECT` (any vector, any level, only to test
the decoder). A fixup never matches by range.

**PIC, PIT, levels (ADR-0009 as amended).** PICs remapped to `0x20` and `0x28`, all masked except
the cascade; `HalConnectInterrupt` unmasks a line. IRQ7 and IRQ15 check the in-service register and
return without EOI when spurious (EOI to the master only for IRQ15). PIT channel 0 mode 2 at about
100 Hz. Per-CPU (one CPU in v0.1, accessed through one function so SMP changes one place): level,
pending software-interrupt mask, soft-interrupt-active flag, count of open `HalDisableInterrupts`
sections. `KeRaiseIrql` to `DEVICE_LEVEL` or above executes `cli`. `KeLowerIrql` drops the level,
then while the dispatch bit is pending and the new level is below `DISPATCH_LEVEL` and no software
interrupt is running, it runs the dispatch handler at `DISPATCH_LEVEL` with `IF` set, on the current
stack (nesting depth 1), and `sti` only when the new level is below `DEVICE_LEVEL`. The same drain runs
at the end of an IRQ whose interrupted level was below `DISPATCH_LEVEL`. The timer handler only
bumps a counter and requests the dispatch interrupt.

**Time and TSC calibration (D16).** `HalQueryMonotonicTime` is `(rdtsc - tsc0) * mult >> 32` in
100 ns units, with `mult = (10^7 << 32) / tsc_hz`, using a 64x64 to 128 bit multiply (no libgcc).
Calibration is **interrupt driven, never polled**: the PIT runs at 100 Hz, the timer handler reads the
TSC as its first instruction and stores it with the tick number; the boot code enables interrupts and
waits in `hlt` until tick 2, records `T0`, waits in `hlt` until tick 52 and records `T1`;
`tsc_hz = (T1 - T0) * PIT_HZ / (52 - 2) / divisor`, with PIT input 1193181.67 Hz (14.31818 MHz / 12)
written as the exact ratio 14318180/12. 50 ticks (0.5 s) bound the interrupt-latency jitter to about
0.2 % of one sample. The source of truth is the PIT as seen by a guest that waits in `hlt`, which is
what A10 measured to follow the host within 1 %. No loop reads the PIT counter in calibration. The
only polled PIT reads are the O8 spins, which are bounded in PIT time and compared with nothing.

**Test hook.** The kernel is the test kernel in v0.1: after initialisation it reads the optional QEMU
fw_cfg file `opt/kamos/test` (signature `QEMU` checked first) to pick a scenario. No key means the
full suite. With no fw_cfg device (real hardware) the kernel prints the banner and idles. Scenarios
that must end in a bug check run in their own boot because a bug check ends the boot.

## 3. Alternatives rejected

- **Limine (64-bit entry) instead of a trampoline.** Would remove the 32 to 64 code, but ADR-0001 is
  decided and the founder confirmed it; not reopened.
- **Calibrate the TSC by polling the PIT counter** (the usual OSDev method). Rejected by D16: under
  TCG the polling guest sees 0.8 of host time. The interrupt-driven method is the same one the
  oracle uses.
- **Kernel mapped with 2 MiB pages only.** Simplest, but `.text` and `.data` would share a page, so
  no W^X (ADR-0005) and no way to test `#PF` for NX fetch or a write to read-only data. 4 KiB pages
  for the image cost about 40 lines of assembly.
- **Selecting the scenario from the GRUB command line.** Needs a menu per scenario and a way to pick
  one without a keyboard. fw_cfg is chosen from the QEMU command line, which the runner already
  controls, and needs no change to `grub.cfg` or to the Makefile.
- **Using `kt_run` as is.** It prints the detail only for FAIL and SKIP, so the timer lines cannot
  carry `t100ns=`. I use `ktest.h`'s primitives in my own loop that prints the detail on PASS too
  (same grammar). I will ask A10 to upstream the one-line change.

## 6. Risks

- **GRUB loading an ELF64 with a high VMA.** The A02 fixture proves it works; detection: first boot.
- **TCG timing (D16) and 1 % margin** (A10 measured 0.79 points of noise already). Detection: O4 run
  10 times per CPU; action: report, do not tune the oracle.
- **Faults during early boot** (triple fault looks like a reset loop with `-no-reboot`: QEMU exits 0 or
  hangs). Detection: `tools/qemu/faults.sh` with `-d int`; I keep the IDT installed before anything
  can fault.
- **Interrupt delivery while a level changes** (lost or doubled dispatch). Detection: the O8 and
  dispatch tests, and `ASSERT`s on the flag and level in the entry and exit paths.
- **Hostile boot information**: the parser runs on a structure written by the loader; every read is
  bounded by the total size, checked once up front, and the size has an upper limit.
- **Toolchain**: `-mgeneral-regs-only` forbids SSE; no `memcpy` from libc exists, GCC may emit calls,
  so rtl provides them. If a 128-bit division is needed it is replaced by a 64-bit one.
- **Clean room (ADR-0012)**: sources are the Intel SDM, the Multiboot2 specification, the 8259,
  8254 and 16550 data sheets, the ACPI RSDP layout, QEMU's public fw_cfg documentation. Nothing is
  taken from Microsoft binaries or leaked material; names follow the public NT vocabulary already in
  the headers.

## 7b. Obligations from A01's message of 2026-10-31 (main 099d7f4) and RFC-0002 R-a to R-c

- The level used by ADR-0013 is the level of the interrupted code, saved by the exception stub in the
  frame; the handler itself runs at `DEVICE_LEVEL`. Tests: a fixup at `PASSIVE_LEVEL` resumes and `IF` and
  the level after it equal the values before the fault, including a fault inside a `HalDisableInterrupts`
  section (`IF` clear); a fault with the level raised to `DEVICE_LEVEL` by the test does not resume
  (O7 c, O8 case 6).
- Software interrupts: depth 1 means a request made while one runs only sets its bit and the running one
  loops. Test (O8 case 7): a dispatch handler requeues itself and a timer tick arrives during it; the
  entry counter never exceeds 1 and the recorded `RSP` is the same each time. "Current stack" in
  Phase 2 is the boot stack (`KiBootStackTop`, 16 KiB) of the single CPU, before A05's threads.
  A handler that requeues itself forever starves the stack's owner; not bounded here (A05's policy).
- IST: three stacks, 8 KiB each, for `#DF` (IST1), NMI (IST2), `#MC` (IST3). Nesting rule: NMI and `#MC`
  have separate stacks so one can interrupt the other; a second NMI while one runs is held by the CPU
  (NMI blocking until `iretq`); `#DF` is fatal and does not return. All three handlers only print and stop
  in v0.1.
- Memory map: the merge rule is the one in `boot.h` as amended (same type merged, different-type overlap,
  wrap, more than 128 regions after merging, no usable region are bug checks).

## 9. Addendum 2026-10-31: changes found by running the code

1. **Calibration estimator.** Section 5 planned an end-point formula over ticks 2 to 52. Measured on this
   host that gave a TSC estimate varying between 2.70 and 2.74 GHz (about 1.4 %, true value near 2.7055
   GHz) and failed the 1 % oracle once in 8 boots. Delivery jitter of single ticks under TCG is about
   a millisecond. A least-squares fit with lost-tick inference was tried next and was wrong: a late tick
   (interval 69383 kcycles followed by 12004, normal 27100) was read as two lost ticks. Final design:
   100 intervals, estimate = median over all 91 windows of 10 consecutive ticks. It is still driven by
   interrupts (the handler reads the TSC first, the boot code waits in `sti; hlt; cli`), so D16's
   obligation is unchanged. Result: 10 boots on qemu64 gave guest/host ratios 0.99609 to 1.00367
   (oracle 0.99 to 1.01).
2. **MBI inside the image bounds.** The release image has a gap between its segments and GRUB placed
   the information structure there (0x10d5a0). `ArchFinishBootMappings` removed that alias, so the
   parser faulted. The boot information is now parsed before the alias is removed. Found by the release
   scenario run, not by the debug run.
3. **In-guest tick cross-check.** `timer end` first required the tick count to match the TSC clock
   within 1 %. On a loaded host ticks were lost (calibration exact, 10 s of ticks more than 1 % short),
   which is a QEMU delivery effect, not a clock error. The check now fails only if ticks run ahead of the
   TSC clock by more than 1 %; the lag is reported as `tick_lag_permille`. The host wall-clock ratio
   (O4) stays the oracle and was not widened.
4. **depth_is_one.** The test compared the stack position of successive handler runs (section 7b); a run
   delivered at the end of the timer IRQ is legitimately lower. It now checks that every run is on the
   current stack, and `SoftMaxDepth == 1` stays the depth check.
