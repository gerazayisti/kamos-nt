# Methodology note, Wave 1, A02 BUILD

Date: 2026-10-31. Branch `agent/a02/p1-build`. Task: `docs/coordination/tasks/W1-A02.md`.
No code, Makefile or workflow change is made before A01 records `Methodology accepted`.

Six deliverables, numbered as in the brief: K (kernel build rules), G (GDB), Q (QEMU profiles),
C (CI, first remote run), R (debug and release profiles), S (clang-format and static analysis).

## 1. Goal in observable terms

- K: `make all iso test` still passes on `qemu64` and `max` with the placeholder, and its
  `kernel.elf` sha256 stays `126129e2be4dc292bf68...` (recorded 2026-10-31). Given C and NASM
  files under `boot/ arch/x86_64/ hal/ ntoskrnl/` plus `arch/x86_64/boot/kernel.ld`, `make all`
  builds and links them. `tools/ci/reproducible.sh` reports both files identical.
- G: `tools/debug/` holds a GDB init and a launcher. `docs/development/toolchain.md` states, with
  the verbatim GDB output, whether `set architecture i386:x86-64` is needed.
- Q: `tools/qemu/` has one script per profile of Annex A.5 (normal, serial, faults, gdb, test,
  disk and monitor), each runnable with `qemu64` and `max`.
- C: `docs/testing/evidence.md` records the first GitHub run (run id, commit, per-job result and
  duration, what had to be fixed). A deliberately broken commit turns CI red; the actions are
  pinned to full SHAs.
- R: `make KAMOS_DEBUG=1` and `make KAMOS_DEBUG=0` build into separate directories; a proposal to
  A01 for `ASSERT` in each.
- S: `.clang-format`, `tools/ci/format-check.sh`, a `static-analysis` CI job that is proven to
  fail on a planted defect.

## 2. Approach

Principle: every check is a script in `tools/` that runs the same way locally and in CI, and
every script has a negative case that proves it can fail.

K. Source discovery with `find` over the four directories, sorted with `LC_ALL=C sort`, so the
link order does not depend on the file system. Pattern rules `.c` to `.o` with `-MMD -MP`, and
`.asm` to `.o` with `nasm -f elf64 -MD -MP -g -F dwarf` using paths relative to the repository
root (so no build path enters the debug info). `-Werror=date-time` is added to `KCFLAGS` next to
the existing `-ffile-prefix-map`. Link: `ld -n -nostdlib --build-id=none -T arch/x86_64/boot/kernel.ld`
with the same options as today, so the placeholder path produces the same bytes. libgcc is not
linked by default. A variable `KERNEL_LIBGCC=1` appends `$(CC) -mno-red-zone -print-libgcc-file-name`
and is switched on only when the link of real code reports an undefined `__udivti3` or similar.
Placeholder: if no source is found under the four directories, the existing placeholder rules are
used unchanged. The moment A03 commits its first source, the real rules apply; that switch is
intended and is announced in my report. Object files go in `build/obj/<config>/`.

G. A launcher script starts QEMU paused (`-s -S`, its own port, a timeout) and GDB in batch mode
(`gdb -batch -x tools/debug/kamos.gdb`). Test subject for the long-mode question: the placeholder
only runs in 32-bit protected mode and never enters long mode, so it cannot answer it. I write a
measurement fixture `tools/debug/fixture/` (about 40 lines of NASM and a linker script, clearly
labelled as a GDB test image, not a kernel) that does the same 32 to 64 bit switch as ADR-0001:
PAE, `EFER.LME`, paging, far jump. The result is repeated against A03's real trampoline when it
exists, and both results are written down.

Q. One shared `tools/qemu/common.sh` (options per profile, timeout, port variables) and one thin
script per profile. The existing `run-test.sh` is kept as the test profile. Each script can print
its final QEMU command line (`--print`), which is what the tests compare with Annex A.5.
Makefile targets `run`, `run-serial`, `debug` call these scripts.

C. Read-only first: watch the run with `gh`, record every job. Fix only what the real runner
shows. A second run proves the cache hit and its duration. The SHA pin is resolved through
`gh api` (tag to commit, dereferencing annotated tags), written as `uses: owner/repo@<40 hex> # vX.Y.Z`,
and enforced by `tools/ci/check-pins.sh` in the `hygiene` job.

R. `KAMOS_DEBUG` (1 or 0) adds `-DKAMOS_DEBUG=1 -O0 -g3` or `-DNDEBUG -O2 -g`; objects and
`kernel.elf` go to `build/debug/` and `build/release/`. The flags are written into a stamp file
that objects depend on, so changing the profile rebuilds. CI builds both.

S. `.clang-format` derived from what exists: 4 spaces (`.editorconfig`), PascalCase functions
(ADR-0008), the style of `sdk/include/kamos/*.h`. I measure candidates with
`clang-format --dry-run` on the A01 headers and keep the one with the fewest differences; I do not
reformat A01's headers. Static analysis: cppcheck 2.13 (`--std=c11 --platform=unix64
--error-exitcode=1 --inline-suppr`), advisory clang-tidy later.

Sources: GNU make manual (automatic prerequisites), GCC manual (`-MMD`, `-MP`, `-ffile-prefix-map`,
`-Wdate-time`, `-mno-red-zone`), GNU ld manual, NASM manual (`-MD`, `-F dwarf`), QEMU
documentation (gdbstub, `-d`, `-D`, monitor), GDB manual (remote debugging, `set architecture`),
OSDev wiki (Libgcc without red zone, already cited in `build-cross.sh`), GitHub documentation
(caching, pinning actions to a full SHA), cppcheck and clang-format manuals. All are public
documentation allowed by ADR-0012.

## 3. Alternatives rejected

- K: a recursive Makefile per directory. Rejected: hidden dependencies and order, harder to make
  reproducible. One top-level Makefile with discovery. CMake was also rejected for now: the plan
  lists it as an option, but the Makefile already passes the placeholder tests and a second build
  system would double the reproducibility work.
- K: always link libgcc. Rejected: it can pull in code that was not wanted; ADR-0003 says "only if
  the kernel needs it".
- G: use the placeholder as the GDB subject. Rejected: it never leaves protected mode, so the
  answer would be vacuous. Waiting for A03's trampoline was also rejected: the fixture gives the
  answer a wave earlier and A03 can use the launcher at once.
- C: let Dependabot's major bumps decide the pins. Rejected as the method; see risks.
- C: split the toolchain into a binutils cache and a GCC cache. Not done now; held in reserve if
  the first remote build times out (a failed job saves no cache).
- S: clang-tidy as the first analyser. Rejected: it needs a compilation database, and the build
  uses a GCC cross compiler. cppcheck works on the files directly.

## 4. Order of work

1. K1. Fixture `tools/ci/fixtures/kernel-c/` (my own tiny C, NASM and linker script, not kernel
   code) plus Makefile variables to point the rules at it. This is the largest uncertainty: no C
   has ever been linked with the cross toolchain; A10 only checked `ld -r`. The first test links
   it with and without libgcc.
2. K2. Discovery, `-MMD`, NASM objects, link, placeholder fallback. Done when the placeholder hash is
   unchanged and the fixture builds. Then hand to A03 (they wait on this).
3. K3. `reproducible.sh` run on the fixture tree as well, plus a check that no build path appears.
4. G1. QEMU gdb profile (the smallest part of Q that G needs), then the long-mode fixture and the
   three GDB variants (section 5). G2. `toolchain.md` with the output.
5. Q. The remaining profiles, then the `max` runs.
6. C, in parallel with the rest since it is mostly waiting: observe, record, second run, red
   proof, then pins. Fix commits only when a job is really red.
7. R when A03 has C code and A01 has answered on `ASSERT`.
8. S: `.clang-format` and `format-check.sh` first; the analysis job when the first C file lands.

Each step is a commit that builds and passes `make all iso test` on both CPUs.

## 6. Risks

- RAM. WSL has 3.9 GB and 2 CPUs (observed with `free -m` and `nproc`). Rule: one build at a time,
  no QEMU run in parallel with a toolchain build, `KAMOS_JOBS=1` locally for GCC. Detect: `free -m`
  before each heavy command. If a build is killed, I rerun with fewer jobs and say so.
- First CI run. Observed at 10:40 UTC: the `toolchain` job is in the build step (cache miss). Its
  length is unknown until it ends. The cache is saved only if the job succeeds (post step of
  `actions/cache`), so a failure or the 240 minute timeout loses everything and the next run starts
  at zero. The cross directory is 1.3 GB locally (`du -sh ~/opt/cross`), well under the 10 GB
  repository cache limit; unused entries are evicted after 7 days. If it times out: split the cache
  as in section 3.
- Parallel cache misses. Observed: three Dependabot pull request runs started at the same minute as
  the main run, so four toolchain builds may run at once. A cache written from a pull request is
  not readable by main, so these runs do not help main and spend runner time. I do not touch them;
  I note them.
- Cache key. The key hashes all of `toolchain/versions.txt` and `build-cross.sh`, and
  `versions.txt` also holds host tool versions (nasm, qemu, clang). Editing a comment or adding a
  host version, for example the clang-format version for S, invalidates the cache and costs
  another one to two hours. I will not edit either file without a reason; if I need host versions
  I split them into a file outside the hash, which itself costs one rebuild. Question to A01.
- Pinning. Dependabot already opened pull requests that bump `checkout` 4 to 7, `cache` 4 to 6 and
  `upload-artifact` 4 to 7 (observed). The first run also shows a Node.js 20 deprecation notice for
  `actions/checkout@v4`. I pin the SHAs of the versions that the run proves green, and then Dependabot
  updates the SHAs; a major bump gets a full CI run before it is accepted. A tag can be moved, so
  I resolve it to a commit and compare it to the release page, and I do not copy a SHA from a pull
  request without that check.
- Job set-up cost. Every job runs `install-deps.sh` (apt update and about 30 packages including
  clang and MinGW). Network failures and package differences on the runner are possible; whether
  `lld-link` exists on the runner is untested (`check-toolchain.sh` requires it). I read the real log.
- Source mirror. `build-cross.sh` downloads from `ftp.gnu.org`; the checksums are pinned, so a bad
  tarball fails, but an outage fails the job. Re-run is the response.
- GDB. QEMU's gdb stub and GDB can disagree on the register set when the mode changes; this is the
  point of G. Also software breakpoints before paging may not work; I test `hbreak`.
- Reproducibility with real C. Sorted inputs, relative paths, `-Werror=date-time`, no timestamps in
  NASM output. Not yet proven: nothing but NASM has been built. K3 detects it before A03 depends on it.
- Placeholder switch. If A03 commits partial sources, the real rules take over and may fail. That
  failure is A03's to see and mine to explain; I do not edit kernel code to make it pass.
- Hygiene. Editing through the UNC path drops the executable bit; after each edit I check
  `git diff --summary` and restore the modes.
