## Acceptance criteria and what was observed

All runs on this machine: WSL Ubuntu 24.04, QEMU TCG, cross GCC 16.2.

- **CI set** (run on the final tree before the commit): `build-test.sh qemu64 debug` PASS,
  `build-test.sh max release` PASS, `spdx-check.sh` PASS, `static-analysis.sh` PASS (16 files),
  `reproducible.sh` identical (kernel.elf 5f37b7771ab3cb21), `reproducible.sh release` identical
  (kernel.elf 97df507761062e52). Host harness: `test-host: PASS`; `test_bootinfo` 15/15,
  `test_format` 5/5, `test_fixup` 4/4 (compiled and run by hand under gcc with ASan and UBSan; the
  mutant that skips entry 1 fails `test_exact_match`).
- **qemu64 and max exit 33.** `tools/ci/build-test.sh qemu64 debug` rc=0, `build-test (qemu64, debug): PASS`.
  `tests/hal/run-scenarios.sh` for debug and release on both `qemu64` and `max`: PASS (full suite and
  8 scenarios).
- **#DE, #UD, #GP, #PF each have a test** (suites `exc` and `pf`, with also #BP as a trap and a
  non-canonical and a selector #GP). The exception line format is in `docs/architecture/interrupts.md`.
- **Deliberate page fault handled per ADR-0013.** Suite `pfpolicy`: a fixup at PASSIVE_LEVEL resumes
  with registers, IF and level as before; the static `.kfixup` entry resumes; a fault in a
  `HalDisableInterrupts` section resumes (IF restored clear). Scenarios `pf-nofixup`, `pf-offbyone`
  (fixup one byte off) and `pf-device` (exact fixup, interrupted level DEVICE) all end in
  `KAMOS STOP 0x00000002 UNHANDLED_EXCEPTION`, exit 37, in both profiles.
- **Double fault on IST.** Scenario `df`: exit 37 with `KAMOS STOP 0x00000003 DOUBLE_FAULT`, handler
  frame at 0xffffffff8011ff60 in the debug build, which lies in `KiDoubleFaultStack` (`nm`: 0xffffffff8011e010,
  8192 bytes, so up to 0xffffffff80120010; compared by hand, not by an automatic assertion).
- **Level masking.** A test raises to DEVICE_LEVEL, checks with the control that a tick is delivered
  at PASSIVE_LEVEL, checks the tick counter does not move at DEVICE_LEVEL, lowers, and checks it
  moves again. RFLAGS comes from `pushfq`. Dispatch: held at DEVICE_LEVEL, run at once at
  PASSIVE_LEVEL, depth 1 (`SoftMaxDepth == 1` with a requeueing handler and a tick during it).
  ASSERT misuse scenarios `irql-raise-down`, `irql-lower-up`, `irql-lower-section`: exit 37 in
  debug; in release they fall through (exit 33, negative control).
- **Timer within 1 % over 10 s (O4, D16).** Calibration is driven by PIT interrupts, the boot code
  waits in HLT and never polls the counter. Final estimator: median over the 91 windows of 10
  consecutive ticks of the TSC cost, 100 intervals. Ten boots of qemu64 debug, host wall clock against
  guest 100 ns clock, allowed 0.99 to 1.01: 1.003666, 0.999190, 1.002867, 0.998503, 1.000915,
  0.997593, 0.999720, 0.996517, 0.999087, 0.996090. All inside. The same runs show the TSC estimate
  between 2706849065 and 2732655712 Hz, so the estimate itself still moves by about 1 % between
  boots and the margin to the 1 % limit is small (the worst ratio is 0.99609). I did not run 10
  boots of `max` for the ratio, and the runs were made while other jobs used the machine.

## What went wrong on the way (the reasons for the addendum in the methodology note)

1. First estimator (end points of 50 intervals): TSC between 2.70 and 2.74 GHz, ratio 0.988 once.
2. Second (least squares with lost-tick inference): a late tick was read as two lost ticks.
3. The release scenarios failed at once in boot: the multiboot information sat in a gap of the image
   (0x10d5a0) and the boot mapping had already removed that alias. The debug image has no such gap
   so the debug run never showed it. Now the boot information is parsed first.
4. `timer end` failed once on `max` (debug): calibration looked exact (2709863518 Hz) but ticks counted
   over 10 s fell short by more than 1 %. I first blamed lost ticks on a loaded machine; that was
   incomplete, see "Revision after A01's review" (the TSC rate itself changed). The in-guest check
   now fails only if ticks run ahead; the lag is printed.

## Revision after A01's review (two blockers)

1. **cppcheck `comparePointers`.** `static-analysis.sh` failed on `__kfixup_end - __kfixup_start`
   (`exception.c:99`). The count is now `__kfixup_count`, computed in `kernel.ld` outside the section
   statement with `ABSOLUTE()` (inside the statement it is section-relative and C saw an address; I hit
   that: the lookup scanned past the table and matched a zero entry, rip=0 resumed at rip=0 in an
   endless loop; found by the first boot after the change). `nm`: `0000000000000001 A __kfixup_count`.
   A link-time `ASSERT` checks whole 16-byte entries. The check stays meaningful: no suppression.
2. **Flaky `run-scenarios.sh release max`.** The failing scenario was `all`, in the timer test, never a
   bug-check scenario (the `qemu exit code: 37` line A01 saw is just the last scenario's exit code, which
   is the expected one for `pf-offbyone`). Observed on 6 runs before the fix: 3 failed, with host/guest
   ratios 1.046, 1.055, 1.072 and a `timer end` FAIL. A10's `noise.sh 8 max` in the same minutes: min
   0.992074, max 1.000529, so QEMU and the host clock were fine. The guest TSC frequency, estimated at
   boot, came out at about 2.706 GHz in some boots and about 2.959 GHz in others (ratio 1.093), and a few
   boots changed rate between the calibration and the test (2.77, 2.885 GHz). A single calibration cannot
   be right on such a host. Fix: the timer handler re-measures the rate every 100 ticks (same median
   estimator) and re-bases the clock under a sequence counter. After it, `a03-o4.sh 8 max release`: 8
   ratios 0.999919, 0.998650, 0.998749, 0.999834, 0.999907, 0.993032, 1.004561, then one run failed on
   a different cause (next point), none outside 0.99 to 1.01. This is a host-environment finding: I have not
   seen it on real hardware, and with an invariant TSC the re-measurement changes nothing.
3. **A second flake, in my tests.** `dispatch held_until_lowered` (once) and `held_at_device` (once)
   failed with one more handler run than expected: the timer tick also requests the dispatch interrupt
   and can land before the sample, or inside the handler. The tests now raise the level first, then
   install the handler and sample, and assert "at least one run" after the lowering (the "held" checks
   before it stay exact).
4. **The 12 outcomes** (`a03-twelve.sh`: build both profiles, then `tests/hal/run-scenarios.sh` three
   times per combination, final tree):
   debug qemu64 PASS PASS PASS; debug max PASS PASS PASS; release qemu64 PASS PASS PASS; release max
   PASS PASS PASS.
5. **Usage.** `tests/hal/run-scenarios.sh` with fewer than two arguments, or a profile that is not
   `debug` or `release`, prints the usage and exits 2. It is not in CI: asked to A02 through the inbox
   (`docs/coordination/inbox/A02.md`); I changed neither `ci.yml` nor the Makefile.
6. **Merge.** `git merge main` done on the branch. Conflicts in `BOARD.md`, `inbox/A01.md`,
   `evidence.md` resolved by keeping both sides, then removing the superseded W1-09, W1-10, W1-11 rows
   that main and I had both edited (main's W1-11 row kept).

## Wave 1 gate: reservations C1 and C2 (A01 decisions)

- **C1, timer band.** `tests/hal/all.manifest` now allows 0.98 to 1.02 for the host/guest ratio under
  QEMU TCG (A10: 0.9918 to 1.0105 over 20 runs). The 1 % band stays the target for KVM and real hardware
  (milestone M-HW); this is written in the manifest. A failed test now keeps its notes in the `KTEST`
  line (`... FAIL <message> | t100ns=... tsc_span=... tick_span=... tick_lag_permille=...`), so a failed
  timer run always has its spans and the ratio can be computed.
- **C2, new tests** (all in `hal/ktest`):
  - M03: the exception handler records `KeGetCurrentIrql()` and RFLAGS.IF as seen inside itself
    (`KiLastException.HandlerIrql`, `.HandlerIf`); `pfpolicy handler_frame` requires DEVICE_LEVEL and IF clear.
  - M10: scenario `fixup-nonpf` registers an exact FIXUP-class entry for a #DE at PASSIVE_LEVEL; the
    kernel must stop (exit 37, `UNHANDLED_EXCEPTION P1=0x0`), manifest `tests/hal/fixup-nonpf.manifest`.
  - M16: `pic spurious7_irq0_in_service`. A test seam (`HalpTestHoldTimerEoi`) withholds the EOI of the
    next timer tick, so IRQ 0 is in service (ISR bit 0 set) when the test fires `int $0x27`; the ISR must
    be unchanged afterwards. The test sends the withheld EOI itself.
  - `depth_is_one` also uses an observation of its own: the test handler counts how many runs of it are
    live at once (`handler_max_active`, must be 1), independent of the HAL's `SoftMaxDepth`.
- **Mutations rerun by me** (scratch copy `/tmp/a03-mut`, debug, qemu64, scripts `a03-mut.sh` and
  `a03-mut2.sh`); the unmutated copy passes `all` and `fixup-nonpf`:
  - M03 (`cpu->Irql = interrupted` in `KiTrapDispatch`): RED, `pfpolicy handler_frame FAIL
    KiLastException.HandlerIrql == DEVICE_LEVEL (0x0 vs 0xc)`, exit 35.
  - M10 (fixup used for any vector): RED, `fixup-nonpf` ends with exit 33 where 37 is expected, no
    `action=stop` line.
  - M16 (EOI on a spurious IRQ 7): RED, `pic spurious7_irq0_in_service FAIL isrAfter == isrHeld (0x0 vs
    0x1)`, exit 35.
  - M11, with the HAL's own counter blinded (guards removed and `SoftMaxDepth` never updated):
    RED, `dispatch depth_is_one FAIL ... | runs=4 handler_max_active=4`; the HAL counter reads 0, the
    handler's own observation reads 4, so the new observation does not depend on the HAL.

## Open

- A10 has not replayed anything. Ratios for `max`, release and repeated runs on a quiet machine are not
  measured by me beyond the one pass each in the scenario runs.
- Lost ticks under load are not compensated for in wall-clock terms on the PIT side (the monotonic
  clock follows the TSC, so it is not slowed, but the tick count that drives the dispatch interrupt
  is).
- SMEP and SMAP are enabled without any `stac`/`clac`; A04's user copy routines must add them.
- The RSDP search does not scan the EBDA. Only the BIOS ROM area is scanned.
- The kernel image still uses 4 KiB boot page tables of its own until A04's tables replace them.
- NMI and #MC only print and stop. No APIC, no SMP, no FPU/SSE state, no user mode.
- `HalRequestDispatchInterrupt` and `HalSetDispatchInterruptHandler` live in `hal/halp.h`; A01 should
  promote them to a public header.
- No automatic check that the #DF frame is inside the IST1 range (read by hand above).
- A04 files appeared untracked in my worktree; I removed two I had committed by mistake (amend before
  any push).
